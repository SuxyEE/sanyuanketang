## 2. 总体判断

当前三元课堂 Demo 对“单教室实时互动”覆盖较好，但招标材料还同时描述了跨校同步、奥威亚录播、循证听评课、集团中控、设备运维和正式交付。经确认，奥威亚录播相关软硬件由奥威亚独立提供，不属于珑道建设、集成或运维范围。珑道侧仍缺少以下四个完整能力域：

1. 主讲校/听讲校和结对组编排；
2. 集团级课堂业务中控与终端告警；
3. 基于数字互动事实和人工量表的教研闭环；
4. 工程、培训、验收和持续运维体系。

补漏后应把产品定义为“核心课堂 + 业务中控 + 可选教研扩展”。奥威亚录播系统独立交付，双方不做设备控制、媒体处理或运行状态集成；只有未来合同明确要求且奥威亚提供正式接口时，才另立项目评估 SSO、页面跳转或外部资源引用。

### 3.1 第二轮核对后的横向缺口

除课堂功能外，还必须把以下能力写进总体设计，否则项目能演示但难以持续交付：

- **产品控制面**：按学校维护版本、模块、并发课堂数、终端数、媒体存储、AI 额度、有效期和试用策略，后端逐请求校验授权，前端菜单隐藏不能代替授权。
- **内容生命周期**：跨校集备、教案/课件版本、审核、引用和修改留痕；课件、在线学习任务和教研成果共用基础元数据，但保持不同业务流程。录播视频资源不进入珑道媒体处理链路。
- **AI 算力控制面**：本地或云端模型节点统一纳管，学校只选择模型场景，不直接接触密钥和推理地址；必须监控 GPU、队列、失败切换、成本和内容安全。
- **未成年人数据治理**：珑道侧重点治理原始作答、讨论内容和 AI 推断；奥威亚侧负责其录音录像、人脸、声纹等数据合规。双方未发生数据交换时不重复保存对方数据。
- **工程版本治理**：API/事件版本、数据库迁移、配置变更、厂商兼容矩阵、灰度发布、回滚、RPO/RTO 和容量成本模型都应进入验收资料。
- **产品命名治理**：代码和内部产品码可继续使用 `sanyuan-classroom`，对外“多元课堂/三元课堂”名称由学校品牌配置决定，但合同、报价、接口和验收文档必须使用同一产品码消除歧义。

## 4. 当前招投标文档需要修正的口径

### 4.1 不能按现货描述的内容

- `apps/admin` 的仪表盘、班级、学生画像、AI 治理等仍大量使用 mock，不能写成完整真实中控。
- 校本题库与课堂尚未真正打通，错题/好题/AI 题回流仍是待开发能力。
- 三校同步课堂只有“学生可以加入同一房间”的技术可能性，没有结对组、主讲/听讲和轮流主讲编排。
- 数据中台和集团驾驶舱尚未实现；奥威亚录播、ASR 和视频 AI 属于外部范围，不能列入珑道待开发清单。
- Skill 技能中心和智能体到课堂的执行接口仍未落地。

### 4.2 必须明确排除的奥威亚范围

- AVA 录播主机、摄像机、话筒、触控面板和互动系统；
- 人脸/肢体跟踪、自动导播、声纹、表情和视频行为分析；
- 奥威亚 AI 教研助手及其专用模型能力；
- 厂商承诺的检测报告、硬件性能和售后服务。

标书应写成“奥威亚录播相关软硬件及平台由奥威亚独立提供、实施和运维，珑道不参与设备控制、媒体处理、视频巡课、录像资源管理或视频循证”。不得再写“珑道通过适配层完成全对接”。未来若新增 SSO、页面跳转或数据交换，应作为独立接口范围重新确认责任、费用和验收标准。

### 4.3 应删除或改写的现有描述

- 删除教师端自带 `apiKey/baseUrl` 的正式产品卖点；模型和密钥必须由学校控制面管理。
- “毫秒级 AI”“准确率不低于 90%”“固定并发数”等必须附测试环境和报告，否则改成可测的性能目标。
- “数据中台”不能用于指代普通管理看板；应明确独立建设范围。
- “学生画像/教师画像”应说明数据来源、维度、更新频率、解释方式和申诉机制。
- “实时全对接”必须给出厂商 API、字段、鉴权、回调和失败补偿；否则标半对接或预留。

## 5. 补漏后的产品工作包

### WP0：产品控制面与合规基线

- 产品套餐、模块 entitlement、额度、有效期、学校品牌和功能开关；
- 本地/云端模型路由、密钥托管、GPU 节点、队列、成本和 AI 审计；
- 未成年人、录音录像、生物特征和跨校数据共享规则；
- API/事件版本、迁移、灰度、回滚、RPO/RTO 和容量基线。

### WP1：核心 SaaS 和学校中控

- SSO、租户、真实班级课表、课堂持久化和 Redis 多实例；
- 校本题库选题、快照、测评和题目效果回流；
- 今日课堂、实时态势、告警、学情和真实管理报表；
- 课堂事件 Outbox 和智慧校园投影。

### WP2：跨校同步课堂

- 结对组、主讲/听讲、排课、预检、子房间和主讲权；
- 跨校备课组、教案/课件版本、协同记录和发布留痕；
- 教师端远端教室状态与分范围下发；
- 分校参与和学情报告；
- 网络中断下的本地降级和补传。

### WP3：课堂终端和 MDM

- MDM 集成、终端策略、批量升级和资产绑定；
- 仅纳管教师端、学生端和课堂应用相关终端；
- 终端健康、告警、工单和操作审计；
- 奥威亚录播主机、摄像机、话筒和视频平台不进入珑道设备台账。

### WP4：教学资源和在线学习

- 教案、课件、任务单、课堂报告等非录播教学资源；
- 审核、版本、授权、检索、引用和课程包；
- 课后任务、学习进度和题库练习；
- 与课堂、题库、听评课和知识库关联；录播视频只在未来明确接口项目中保存外部引用，不复制和加工媒体。

### WP5：循证听评课和教师发展

- 数字互动事实 + 人工量表 + 厂商分析的证据融合；
- 数字课堂事件形成的参与、问答、作答、时间分配和教学环节；
- 网络教研活动、签到、笔记、点评、评审和研修共同体成果；
- 可解释的 S-T、布鲁姆、4MAT 建议；
- 教师异议、更正、报告审核和数据保留策略。

### WP6：数据、交付和运维

- 课堂主题事实表和智能问数语义模型；
- 接口、事件、字段映射、质量和对账；
- 现场勘查、安装联调、培训、测试和验收；
- 监控告警、备份恢复、应急预案、升级和 SLA。

## 6. 推荐实施顺序

```text
核心安全止血
  -> 产品授权/合规基线
  -> SSO/租户/主数据
  -> 课堂事实持久化
  -> 题库与学情纵向闭环
  -> 学校真实中控
  -> 跨校同步编排
  -> 课堂终端/MDM
  -> 教学资源与在线学习
  -> 数字循证教研与集团驾驶舱
```

跨校和教研扩展不能反过来阻塞核心课堂。第一轮可验收成果仍应是：真实教师进入真实班级，从校本题库抽题，全班作答，结果可靠回流智慧校园并在学校业务中控可见。奥威亚录播不进入本路线。

## 7. 关键依赖和决策

启动跨校和终端开发前必须取得：

1. 三所学校的网络拓扑、出口带宽、NAT/防火墙和教室点位；
2. 主讲/听讲排课和跨校数据共享规则；
3. 数据中台/驾驶舱的真实接口责任方和指标口径；
4. MDM 产品选型及可调用能力；
5. 本地 AI 算力节点、模型清单、网络边界、并发和运维责任方；
6. 奥威亚与珑道的系统边界确认书，明确默认无接口、无联调、无联合验收。

这些依赖未明确时，只能完成产品设计和模拟适配，不能承诺真实设备全链路验收。

## 8. 首批验收场景

1. 单校 50 台终端同时入课、答题、批改和断线恢复。
2. 题库母题抽取后发布，题库修改不影响历史课堂快照。
3. 一主两从同步课堂完成预约、预检、开课、互动和分校报告。
4. 管理者在中控看到真实课堂业务状态、终端、学情和异常，不依赖 mock。
5. 课后任务、学习进度和题库练习形成完整记录。
6. 教研人员基于数字课堂事件完成量表评价和报告归档。
7. 所有事件重复投递不产生重复成绩、资源或统计。
8. 跨校越权、匿名访问、未授权导出和设备控制全部被拒绝并记录审计。
9. 套餐到期、额度耗尽和未订阅模块在前后端均被一致限制，授权变更有审计记录。
10. 版本升级失败可回滚，数据库、配置和课堂事件在约定 RPO/RTO 内恢复。

## 9. 结论

当前最需要补的不是更多课堂互动按钮，而是三条基础能力：

- **中控真实化**：从 mock 驾驶舱变成基于课堂事件的学校/集团运行中心；
- **跨系统可靠化**：题库、智慧校园、智能体、问数和设备全部通过有身份、有范围、可重试的契约联动；
- **招标边界清晰化**：核心自研、第三方硬件、可选增值和独立数据平台分开报价、分开验收。

完成这些后，三元课堂才从“功能丰富的课堂 Demo”升级为可投标、可交付、可运维、可扩展的教育 SaaS 产品族。
